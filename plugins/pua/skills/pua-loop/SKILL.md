# PUA Loop — 显式迭代 + 验证门控

PUA Loop 在当前 Agent 会话内重复执行“诊断 → 最小动作 → 验证 → 复盘”，直到验收通过、用户暂停，或出现无法自主解除的外部阻塞。

本仓库只发布独立 Skill，不附带上游 setup script 或 Stop hook。因此：

- 不运行任何上游 setup script；
- 不声称存在独立 Oracle 或自动拒绝完成信号；
- 当前 Agent 负责每轮执行验证并保存证据；
- CI、外部 verifier 和用户验收仍是高于 Agent 自评的最终裁决。

## 启动

用户调用 `/pua:pua-loop` 并给出任务后：

1. 加载 `pua` Skill 的三条红线、方法论和压力升级规则。
2. 从用户请求、项目脚本和现有测试中确定 `verify_command`。能够自行查到时直接确定；存在多个会改变验收结果的合理选择时询问用户。
3. 创建或更新 `.pua-loop/state.md`，记录：
   - 任务和验收标准；
   - `verify_command`；
   - 当前迭代数；
   - 已尝试方案和排除项；
   - 最近验证输出；
   - 下一假设。
4. 告知用户循环已经启动、验证命令和暂停方式，然后开始第一轮。

`verify_command` 在循环中保持稳定。若必须改变验收方式，先说明原因并获得用户确认；不能为了让结果通过而降低标准。

## 每轮循环

每轮严格执行：

1. 读取 `.pua-loop/state.md` 和最近相关 diff。
2. 根据当前证据形成一个可证伪假设。
3. 执行能够验证该假设的最小动作。
4. 运行 `verify_command`，保留命令、退出码和关键输出。
5. 更新 state：本轮动作、结果、新排除项和下一假设。
6. 判定：
   - 验证通过且验收项全部满足 → 进入完成门控；
   - 验证失败 → 开始下一轮；
   - 缺少权限、凭证或用户决策 → 暂停；
   - 目标客观不可实现或需要改变结果 → 中止并上报。

## 连败转向

| 连续失败轮次 | 当前 Agent 必须采取的动作 |
|---:|---|
| 1–2 | 读取完整验证输出，修正当前假设 |
| 3–4 | 列出至少 3 个互斥假设，选择证据最强者 |
| 5–7 | 回到需求和系统边界，检查是否一直在解决错误问题 |
| 8+ | 输出阶段复盘，明确已排除项；若仍有新路径则继续，否则暂停并请求必要输入 |

参数微调、重跑同一命令或换函数名不算新方案。转向必须改变假设、观测位置或实现路径。

## 完成门控

宣布完成前必须同时满足：

- 核心行为和明确验收项已经实现；
- `verify_command` 在最终状态下实际运行且退出成功；
- 同类问题和直接回归面已检查；
- 临时诊断代码、调试日志和无用状态已清理；
- 最终报告包含验证命令、输出摘要和残余风险。

满足后输出普通完成报告；不要使用任何暗示外部 Oracle 已验证的 promise 标记。

## 暂停与中止

### 暂停

需要用户提供配置、权限或结果取向时：

1. 更新 `.pua-loop/state.md`；
2. 写明唯一阻塞点和恢复后的第一步；
3. 返回用户，等待输入。

### 中止

用户调用 `/pua:pua-loop stop` 时，先输出当前迭代、验证状态和已创建资源清单，再删除 `.pua-loop/state.md`。只清理由本次 loop 明确创建且用户已授权清理的 worktree、进程或 pane；其余资源仅报告，不擅自删除。

只有以下情况可以中止：

- 目标无法在现有权限或环境中实现；
- 继续需要改变用户已经确认的结果；
- 验证标准彼此矛盾；
- 用户明确停止。

中止报告必须包含已验证事实、尝试记录、排除项、阻塞原因和推荐下一步。不得把“已经尝试很多次”本身当作中止理由。
